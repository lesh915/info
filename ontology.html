OPER 010

온톨로지와 지식그래프, 무엇을 만들고 있는가

용어를 먼저 정확히 구분해야 산출물의 범위가 흔들리지 않는다.

현장에서 “지식그래프 만들자”는 말은 서로 다른 네 가지를 뜻한다. 어떤 팀은 용어사전을, 어떤 팀은 분류체계를, 어떤 팀은 RDF 트리플 저장소를 떠올린다. 첫 회의에서 이 층위를 합의하지 않으면 3개월 뒤 “이건 그냥 엑셀 용어집 아니냐”는 말이 나온다.

1.1 지식 표현의 스펙트럼

지식 표현은 이산적인 종류가 아니라 형식성(formality)의 연속선이다. 아래로 갈수록 사람이 읽기 쉽고, 위로 갈수록 기계가 추론하기 쉽다.

온톨로지는 “무엇이 존재할 수 있는가”를 규정하고, 지식그래프는 “실제로 무엇이 존재하는가”를 담는다. 이 프로젝트의 실패 시나리오 1순위는 온톨로지만 정교하게 만들고 인스턴스 적재를 뒤로 미루는 것이다. 스키마 1개 만들 때마다 인스턴스 10건을 즉시 넣어 검증하라.

1.2 왜 관계형 DB나 벡터 검색으로는 부족한가

RDB만 쓸 때
가변 홉 탐색이 불가능

“이 프로시저를 고치면 영향받는 화면 → 요청서 → 테스트”는 홉 수가 데이터마다 다르다. RDB에서는 재귀 CTE로 흉내 낼 수 있지만, 관계 종류가 20개를 넘어가면 조인 지옥이 된다.

벡터 검색만 쓸 때
“왜 그렇게 답했는지”가 없다

임베딩 유사도는 “착공”과 SP_TRACK_IN이 비슷하다고는 말해도, 그 근거가 컬럼 코멘트인지 커밋 메시지인지 사람 승인인지 남기지 못한다. 감사 추적이 필요한 제조 IT에서는 치명적이다.

지식그래프는 이 둘의 결합이다. 관계는 그래프로 탐색하고, 후보 발굴은 벡터로 하고, 근거는 관계 속성에 남긴다. 이 문서 전체가 이 세 문장의 각주라고 보면 된다.

2.1 버리는 것

  • 완전한 형식 명세를 선행하는 워터폴 — MES 요청서는 진행 중 바뀐다. 스키마도 바뀐다는 전제로 시작한다.
  • OWL 풀 추론 의존 — 추론기 성능·운영 복잡도 대비 이득이 작다. 필요한 추론은 Cypher 규칙으로 명시적으로 구현한다(OPER 080).
  • 도메인 전체 온톨로지 구축 — 반도체 제조 전체를 모델링하려 들면 끝나지 않는다. 역량 질문에 답하는 데 필요한 만큼만 만든다.

OPER 030

역량 질문 설계 — 온톨로지의 요구사항 명세

스키마를 그리기 전에, 그래프가 답해야 할 질문 목록부터 확정한다.

역량 질문(Competency Question, CQ)은 온톨로지 공학의 단위 테스트다. “이 온톨로지가 완성되면 시스템은 이 질문에 답할 수 있어야 한다”를 자연어로 적어두고, 나중에 그 질문을 Cypher로 옮겨 통과 여부를 판정한다.

3.1 좋은 CQ와 나쁜 CQ

나쁜 CQ
“MES 개발 현황을 알 수 있는가?”

범위가 무한하고 정답 판정이 불가능하다. 어떤 스키마 요소가 필요한지 도출되지 않는다.

“착공이 무엇인가?”

용어사전으로 충분하다. 관계가 필요 없으면 그래프를 만들 이유가 없다.

좋은 CQ
“요청서 REQ-2026-0142의 2차 리비전에 등장한 비즈니스 용어 중, 실제 변경된 코드와 연결되지 않은 용어는 무엇인가?”

정답 집합이 유일하게 결정되고, 필요한 클래스(DevRequest, RequestRevision, BusinessTerm, CodeElement)와 관계(HAS_REVISION, MENTIONS, MAPS_TO, REFERS_TO, IMPLEMENTED_BY, MODIFIES)가 즉시 도출된다.

CQ 작성 3원칙

  1. 정답이 유한 집합이어야 한다. “~에 대해 설명하라”는 CQ가 아니다.
  2. 답에 등장하는 명사가 클래스 후보, 동사가 관계 후보다. 이 도출이 안 되면 질문이 너무 추상적인 것이다.
  3. 실제 이해관계자의 입에서 나온 문장이어야 한다. 설계자가 지어낸 CQ는 아무도 안 쓴다.

4.2 정규화 규칙

추출된 표면형(surface form)을 표제어(canonical term)로 접는 규칙을 명문화한다. 이 규칙이 없으면 “착공/착공처리/착공 처리/Track In/TrackIn”이 5개 노드가 된다.

정규화 규칙 정의YAML
normalization:
  # 1) 공백·기호 제거 후 비교
  strip: ["\\s", "-", "_", "\\."]
  # 2) 한국어 접미 동사 제거 (요청서에 흔한 패턴)
  ko_suffix_strip: ["처리", "하기", "함", "됨", "작업", "기능"]
  # 3) 영문 식별자 분해 : camelCase / PascalCase / SNAKE_CASE
  identifier_split: true          # SP_TRACK_IN -> [SP, TRACK, IN]
  # 4) MES 접두사 사전 (분해 시 의미 부여)
  prefix_dict:
    TB_: table
    VW_: view
    PKG_: plsql_package
    SP_: stored_procedure
    FN_: function
    EI_: equipment_interface
  # 5) 표제어 선정 우선순위
  canonical_priority:
    - enterprise_glossary   # 전사 용어사전에 있으면 무조건 그것
    - common_code_master    # 다음은 공통코드 한글명
    - highest_frequency     # 그다음 요청서 출현 빈도 최다형

4.3 동의어와 동음이의어

두 문제는 반대 방향이며, 처리 방식도 반대다.

가장 흔한 설계 실수

BusinessTerm.term 하나만 유니크 키로 잡는 것. 반도체 MES는 Fab / Probe / Assembly / Test 공정별, 그리고 Site별로 같은 단어가 다른 것을 가리킨다. 유니크 키는 반드시 (term, processArea, site) 복합 키여야 한다. 이걸 나중에 바꾸려면 그래프 전체를 재적재해야 한다.

OPER 050

개념 계층화 — 클래스인가 인스턴스인가

온톨로지 초심자가 가장 많이 틀리는 지점, 그리고 MES에서의 판단 기준.

5.1 계층 구축 전략 3가지

Top-down
상위 개념부터

Artifact → Document → DevRequest 순으로 내려온다. 일관성이 좋지만 현실 데이터와 안 맞는 상위 개념을 만들기 쉽다.

Bottom-up
구체 개념부터

실제 요청서·커밋에서 나온 것부터 묶어 올라간다. 현실 적합도는 높지만 계층이 들쭉날쭉해진다.

본 프로젝트는 Middle-out을 채택한다. 가장 자주 쓰이는 중간 수준 개념 (DevRequest, Commit, CodeElement, BusinessTerm)에서 시작해 필요할 때만 위(Artifact)와 아래(PLSQLObject)로 확장한다. 이유는 단순하다 — 역량 질문에 등장하는 명사가 대부분 중간 수준이기 때문이다.

5.2 클래스 vs 인스턴스 판별 규칙

“Lot은 클래스인가 인스턴스인가?”는 반드시 나오는 질문이다. 답은 “무엇에 대해 말하고 싶은가”에 달려 있다.

대상본 그래프에서의 처리이유
Lot(랏) 개념 자체DomainEntity {name:'Lot'} — 인스턴스 우리는 개별 랏 데이터(LOT-A1234)를 추적하지 않는다. “이 용어가 랏에 관한 것”이라는 태깅만 필요하다. 개념을 데이터로 다루므로 인스턴스가 맞다.
실제 랏 LOT-A1234그래프에 넣지 않음 운영 데이터는 MES DB에 있다. 개발 지식그래프의 범위가 아니다. 넣는 순간 노드 수가 억 단위가 된다.
개발요청서 REQ-2026-0142:DevRequest 라벨의 인스턴스 노드 개별 요청서가 추적 대상이다.
“착공”:BusinessTerm 인스턴스용어 자체가 1급 데이터.
PL/SQL 프로시저라는 범주:CodeElement:PLSQLObject 라벨 범주는 Neo4j에서 라벨로 표현한다. LPG에는 클래스 계층이 없으므로 다중 라벨로 대체한다.
판별 규칙

“이것의 개별 사례를 하나씩 노드로 만들 것인가?” — 예면 그것은 클래스(=라벨), 아니오면 인스턴스(=노드)다. 반도체 MES 도메인 개체(Lot, Wafer, Carrier, Recipe)는 개발 지식그래프에서 태깅 어휘로만 쓰이므로 전부 인스턴스로 둔다.

관계 설계 — 그래프의 진짜 자산

노드는 명사, 관계는 동사. 관계 설계를 대충 하면 그래프는 그냥 비싼 태그 시스템이 된다.

6.1 관계 정의 5요소

모든 관계는 아래 5요소를 문서화한 뒤에 구현한다. METHONTOLOGY의 “이항 관계표”를 확장한 형식이다.

관계명은 대문자 스네이크 + 능동태 현재형으로 통일한다. (a)-[:MODIFIES]->(b)를 “a modifies b”로 읽어 문장이 성립해야 한다. REL_1, HAS_DATA 같은 무의미한 이름은 6개월 뒤 아무도 못 읽는다. 특히 HAS_ 접두사는 소유 관계에만 쓰고, 그 외에는 진짜 동사를 찾아라.

6.2 다항 관계 문제와 Reification

“착공은 SP_TRACK_IN에 매핑된다”는 이항 관계다. 그런데 실제로 필요한 정보는 이렇다:

“2026-07-12에 임베딩 모델 v3가 착공을 SP_TRACK_IN에 0.87 신뢰도로 매핑했고, 김OO이 2026-07-15에 승인했으며, 근거는 “컬럼 코멘트: 착공시각”이다.”

이것은 7항 관계다. 표현 방법은 두 가지이며, LPG와 RDF의 가장 큰 차이가 여기서 드러난다.

채택 기준

관계를 노드로 승격(reify)할 조건은 하나다 — “그 관계 자체에 다시 관계를 연결해야 하는가?” 단순히 속성이 많다는 이유로 reify하면 그래프가 두 배로 커지고 모든 질의가 길어진다. 본 프로젝트에서 reify 대상은 TermMapping(휴먼 검토 워크플로가 붙음) 하나뿐이다.

OPER 070

모델링 패턴 카탈로그

반복해서 등장하는 다섯 가지 구조. 매번 새로 고민하지 말고 패턴을 적용하라.

패턴 1 · 리비전(Revision) — 바뀌는 요청서 다루기

요청서가 중간에 바뀐다는 것은 이 프로젝트의 전제 조건이다. 세 가지 선택지가 있다.

  1. 덮어쓰기 — 최신 상태만 유지. 구현은 가장 쉽지만 “2차 시점 기준으로 뭘 개발했나”에 영원히 답할 수 없다. 탈락.
  2. 관계에 유효기간 — 모든 관계에 validFrom/validTo. 유연하지만 모든 질의에 시간 필터가 붙어 복잡도가 폭발한다. 과설계.
  3. 불변 리비전 체인 — 수정 시 새 리비전 노드 생성, 기존 노드 불변. 채택.
리비전 생성 — 멱등 적재CYPHER
// 새 리비전 생성 + 기존 latest 해제
MATCH (r:DevRequest {reqId:$reqId})
OPTIONAL MATCH (r)-[old:HAS_REVISION {isLatest:true}]->(:RequestRevision)
SET old.isLatest = false
WITH r
MERGE (rev:RequestRevision {reqId:$reqId, revNo:$revNo})
  ON CREATE SET rev.revisedAt = datetime($revisedAt),
                rev.revisedBy = $revisedBy,
                rev.changeSummary = $changeSummary
MERGE (r)-[nr:HAS_REVISION]->(rev)
  SET nr.isLatest = true
WITH r, rev
OPTIONAL MATCH (r)-[:HAS_REVISION]->(prev:RequestRevision {revNo:$revNo-1})
FOREACH (_ IN CASE WHEN prev IS NULL THEN [] ELSE [1] END |
  MERGE (rev)-[:PREVIOUS_REVISION]->(prev))
RETURN rev;

// 섹션 적재 : 내용 해시가 같으면 새로 만들지 않고 이전 것을 참조
UNWIND $sections AS sec
MATCH (rev:RequestRevision {reqId:$reqId, revNo:$revNo})
OPTIONAL MATCH (:RequestRevision {reqId:$reqId, revNo:$revNo-1})
              -[:HAS_SECTION]->(old:RequestSection {sectionType:sec.type, contentHash:sec.hash})
CALL {
  WITH rev, sec, old
  WITH rev, sec, old WHERE old IS NOT NULL
  MERGE (rev)-[:HAS_SECTION]->(old)          // 재사용
  RETURN 0 AS x
  UNION
  WITH rev, sec, old
  WITH rev, sec WHERE old IS NULL
  CREATE (s:RequestSection {sectionType:sec.type, content:sec.content,
                            contentHash:sec.hash, revNo:rev.revNo})
  MERGE (rev)-[:HAS_SECTION]->(s)
  RETURN 1 AS x
}
RETURN count(*);

자동 생성된 관계와 사람이 승인한 관계를 구분하지 못하면, 6개월 뒤 그래프를 아무도 신뢰하지 않는다. 모든 매핑 관계에 아래 4속성을 필수로 강제한다.

“일단 관계만 만들고 근거는 나중에” — 나중은 오지 않는다. 근거 없는 관계 10만 개가 쌓이면 전수 재검증이 불가능해져 그래프를 폐기하고 다시 만들게 된다. 적재 단계에서 method가 없으면 트랜잭션을 실패시켜라.

패턴 3 · 브리지 노드 — 두 세계를 잇는 최단 경로 찾기

서로 다른 두 축을 연결할 때, 무작정 N:M 매칭을 시도하기 전에 양쪽이 공유하는 식별자가 있는지 먼저 찾아라. 이 프로젝트에서 그것은 화면 ID(Program ID)다.

예시

요청서 캡쳐 이미지와 소스코드는 아무 공통점이 없어 보인다. 그러나: 캡쳐 화면 타이틀바에 WIP0101이 찍혀 있고, MES 메뉴 마스터에 WIP0101 = 재공 조회가 있고, 소스 파일명이 Wip0101Controller.java라면 — 이미지에서 코드까지 확정적 경로가 생긴다. 임베딩 유사도 0.72짜리 추측보다 이 경로 하나가 훨씬 가치 있다.

패턴 4 · 스코프 한정자 — 동음이의어 격리

OPER 040에서 다룬 (term, processArea, site) 복합 키가 이 패턴이다. 추가로 ABOUT → DomainEntity 관계로 “이 용어가 무엇에 관한 것인지”를 명시하면, 매핑 엔진이 후보를 좁힐 때 결정적 힌트가 된다.

패턴 5 · 부정 정보의 명시 — “매칭 실패”도 데이터다

매칭에 실패한 용어를 그냥 관계 없이 두면, “아직 처리 안 한 것”과 “시도했지만 못 찾은 것”을 구분할 수 없다. 처리 상태를 노드 속성으로 명시한다.

매칭 시도 상태 기록CYPHER
MATCH (bt:BusinessTerm {term:$term, processArea:$area, site:$site})
SET bt.mappingStatus = $status,        // PENDING | MATCHED | NO_CANDIDATE | REJECTED
    bt.lastAttemptAt = datetime(),
    bt.lastAttemptRunId = $runId,
    bt.candidateCount = $candidateCount
RETURN bt.term, bt.mappingStatus;

NO_CANDIDATE가 많은 용어군은 사전 보강이 필요하다는 신호이고, REJECTED가 많으면 매핑 알고리즘이 잘못됐다는 신호다. 둘은 완전히 다른 조치를 부른다.

8.2 그래도 온톨로지의 형식성은 포기하지 않는다

Neo4j에는 스키마 개념이 약하다. 이를 보완하기 위해 스키마를 데이터로 그래프 안에 넣는다. 메타 노드를 만들어 “어떤 관계가 어떤 라벨 사이에 허용되는가”를 명시하고, 이를 검증 질의로 강제한다.

메타 스키마 노드 + 위반 검출CYPHER
// 1) 스키마 자체를 그래프에 등록
MERGE (:RelSchema {relType:'MAPS_TO',
                   fromLabel:'BusinessTerm', toLabel:'TechnicalTerm',
                   requiredProps:['confidence','method','evidence']});
MERGE (:RelSchema {relType:'REFERS_TO',
                   fromLabel:'TechnicalTerm', toLabel:'CodeElement',
                   requiredProps:['confidence','method']});

// 2) 도메인/레인지 위반 검출 (야간 배치로 실행)
MATCH (a)-[r:MAPS_TO]->(b)
WHERE NOT (a:BusinessTerm AND b:TechnicalTerm)
RETURN labels(a) AS fromLabels, labels(b) AS toLabels, count(*) AS violations;

// 3) 필수 속성 누락 검출
MATCH ()-[r:MAPS_TO]->()
WHERE r.confidence IS NULL OR r.method IS NULL OR r.evidence IS NULL
RETURN count(r) AS missingProvenance;
설계 결론

온톨로지는 RDF/OWL 스타일로 설계하고, 구현은 LPG로 한다. 설계 문서에는 클래스·도메인/레인지·카디널리티를 형식적으로 적되, 물리 구현은 Neo4j 라벨/관계/제약으로 옮기고, 형식 제약은 검증 질의(§OPER 130)로 대체한다. 이 분리가 “설계의 엄밀함”과 “운영의 단순함”을 동시에 확보하는 현실적인 타협점이다.

OPER 090

Neo4j 물리 설계

라벨·제약·인덱스·벡터 인덱스. 그리고 되돌리기 어려운 결정들.

9.1 되돌리기 어려운 결정 3가지

  1. 유니크 키 구성 — 나중에 바꾸면 전 노드 재적재. (예: BusinessTerm의 복합 키)
  2. 다중 라벨 vs 속성 — :CodeElement:PLSQLObject로 갈지 :CodeElement {kind:'PLSQL'}로 갈지. 라벨은 인덱스 단위이므로 질의에서 자주 필터링하는 축은 라벨로 둔다.
  3. 임베딩 차원 — 벡터 인덱스는 차원 고정. 모델 교체 시 인덱스 재생성이 필요하므로 embeddingModel 속성을 반드시 함께 저장한다.

9.3 멱등 적재 규약

파이프라인은 언제든 재실행될 수 있어야 한다. 재실행해도 결과가 같아야 한다(idempotency). 아래 4규칙을 코딩 표준으로 강제한다.

  • 모든 노드는 자연키로 MERGE. 자동 증가 ID나 UUID를 키로 쓰지 않는다.
  • ON CREATE SET과 ON MATCH SET을 구분. 생성 시각은 덮어쓰지 않는다.
  • 관계도 MERGE 후 SET. CREATE로 만들면 재실행 시 중복 관계가 생긴다.
  • 모든 쓰기에 pipelineRunId 기록. 특정 실행분만 롤백 가능해야 한다.

import cv2, numpy as np

# MES 화면 UI에도 빨강이 쓰이므로(경고 아이콘 등) 채도·명도 하한을 높게 잡는다
RED_RANGES = [((0, 120, 90), (10, 255, 255)),      # Hue 0 근처
              ((170, 120, 90), (180, 255, 255))]   # Hue 180 근처(빨강 wrap)

def detect_annotations(img_path, min_area_ratio=0.004):
    img = cv2.imread(img_path)
    h, w = img.shape[:2]
    hsv = cv2.cvtColor(img, cv2.COLOR_BGR2HSV)

    mask = np.zeros((h, w), np.uint8)
    for lo, hi in RED_RANGES:
        mask |= cv2.inRange(hsv, np.array(lo), np.array(hi))

    # 얇은 선을 닫아 사각형 윤곽으로 만든다
    mask = cv2.morphologyEx(mask, cv2.MORPH_CLOSE, np.ones((5, 5), np.uint8))
    contours, _ = cv2.findContours(mask, cv2.RETR_EXTERNAL, cv2.CHAIN_APPROX_SIMPLE)

    regions = []
    for c in contours:
        x, y, cw, ch = cv2.boundingRect(c)
        if cw * ch < h * w * min_area_ratio:      # 노이즈 제거
            continue
        peri = cv2.arcLength(c, True)
        approx = cv2.approxPolyDP(c, 0.03 * peri, True)
        shape = "box" if len(approx) == 4 else "arrow_or_circle"
        regions.append({
            "bbox": [x, y, cw, ch],
            "annotationType": shape,
            # 그린 선 안쪽만 잘라 OCR에 넘긴다 (테두리 2px 제외)
            "crop": img[y+2:y+ch-2, x+2:x+cw-2],
        })
    # 위→아래, 좌→우 순서로 정렬해 order 부여 (요청자의 설명 순서와 대개 일치)
    regions.sort(key=lambda r: (r["bbox"][1], r["bbox"][0]))
    for i, r in enumerate(regions):
        r["order"] = i + 1
    return regions

PREFIX_MEANING = {"SP": "stored procedure", "FN": "function", "PKG": "package",
                  "TB": "table", "VW": "view", "EI": "equipment interface"}
ABBREV = {"WIP": "work in process 재공", "EQP": "equipment 설비",
          "LOT": "lot 랏", "HIST": "history 이력", "RSN": "reason 사유",
          "TRACK_IN": "track in 착공", "TRACK_OUT": "track out 완공",
          "CST": "cassette 카세트", "RCP": "recipe 레시피"}

def expand_identifier(qname: str) -> str:
    """SP_TRACK_IN  ->  'stored procedure track in 착공 | SP_TRACK_IN'
    원문도 함께 남겨 정확 일치 신호를 잃지 않는다."""
    tokens, out = qname.replace(".", "_").split("_"), []
    i = 0
    while i < len(tokens):
        two = "_".join(tokens[i:i+2])
        if two in ABBREV:
            out.append(ABBREV[two]); i += 2; continue
        t = tokens[i]
        out.append(PREFIX_MEANING.get(t) or ABBREV.get(t) or t.lower())
        i += 1
    return " ".join(out) + " | " + qname

    return session.run(VECTOR_SEARCH, k=k, queryVector=vec,
                       minScore=min_score, layer=layer).data()

12.4 신뢰도 결합

여러 방법이 같은 매핑을 지지하면 신뢰도가 올라가야 한다. 단순 평균은 틀린 답이다 (규칙 1.0과 임베딩 0.5의 평균 0.75는 규칙 단독보다 나쁘다). 노이지-OR 결합을 사용한다.

Ccombined = 1 − ∏i (1 − wi · ci)
wrule=1.00   wstandard=0.95   wembedding=0.70   wllm=0.65   wvlm=0.55

예) 규칙 0.95 + 임베딩 0.80 이 동시에 지지
= 1 − (1 − 1.00·0.95)(1 − 0.70·0.80) = 1 − 0.05 × 0.44 = 0.978

단, 휴먼 승인(method='human')은 결합 대상이 아니라 덮어쓰기다 → 1.0 고정

12.6 매칭률 산식

BT(R, rev) = rev 리비전의 섹션 텍스트(MENTIONS) + 첨부 캡쳐(MENTIONS_IN_IMAGE)에서 추출된 BusinessTerm 집합

matched(t) = 다음 경로 중 하나라도 존재하면 1
  (a) t —MAPS_TO→ TechnicalTerm —REFERS_TO→ CodeElement
  (b) t —MAPS_TO→ TT —ANCHORED_BY→ StandardTerm 경유 경로
  (c) t —ALIGNS_WITH→ CodeElement
  (d) [이미지] t 등장 ImageRegion —POINTS_TO→ UIElement —BOUND_TO→ DBObject
     또는 ScreenCapture —DEPICTS_SCREEN→ ScreenProgram —RENDERED_BY→ CodeElement
  조건: 경로상 모든 관계의 min(confidence) ≥ θ

매칭률(R, rev, θ) = Σ matched(t) / |BT(R, rev)|

파생 지표 세 가지

  • 가중 매칭률 — 용어 출현 빈도로 가중. 한 번 스쳐간 용어와 20번 나온 핵심 용어를 같게 볼 수 없다.
  • 구현 매칭률 — 경로 종단의 코드가 이 요청의 실제 변경 커밋에 포함될 때만 인정. “코드 어딘가와 매칭”이 아니라 “이번에 실제로 바뀐 코드와 매칭”을 본다. 이것이 진짜 지표다.
  • 모달리티별 매칭률 — text-only / image-only / both로 분해해 이미지 파이프라인의 기여도를 증명한다.
구현 매칭률 (이미지 경로 포함)CYPHER
MATCH (r:DevRequest {reqId:$reqId})-[:HAS_REVISION]->(rev:RequestRevision {revNo:$revNo})
MATCH (rev)-[:HAS_SECTION]->(s:RequestSection)

// 텍스트 유래 용어 + 이미지 유래 용어를 합집합으로
OPTIONAL MATCH (s)-[:MENTIONS]->(bt1:BusinessTerm)
OPTIONAL MATCH (s)-[:HAS_CAPTURE]->(:ScreenCapture)-[:HAS_REGION]->(:ImageRegion)
              -[:MENTIONS_IN_IMAGE]->(bt2:BusinessTerm)
WITH r, collect(DISTINCT bt1) + collect(DISTINCT bt2) AS raw
UNWIND raw AS bt
WITH r, collect(DISTINCT bt) AS terms
UNWIND terms AS bt

// 경로 (a) : 용어 → 개발용어 → 코드, 그리고 그 코드가 이번에 실제 변경됐는가
OPTIONAL MATCH pText = (bt)-[m:MAPS_TO]->(:TechnicalTerm)-[rf:REFERS_TO]->(ce:CodeElement)
  WHERE m.confidence >= $theta AND rf.confidence >= $theta
    AND EXISTS { MATCH (r)-[:IMPLEMENTED_BY]->(:Commit)-[:MODIFIES]->(ce) }

// 경로 (d) : 캡쳐의 주석 영역 → UI 요소 → 컬럼
OPTIONAL MATCH pImg = (bt)<-[:MENTIONS_IN_IMAGE]-(:ImageRegion)-[pt:POINTS_TO]->(:UIElement)
                      -[bd:BOUND_TO]->(db:DBObject)
  WHERE pt.confidence >= $theta AND bd.confidence >= $theta
    AND EXISTS { MATCH (r)-[:IMPLEMENTED_BY]->(:Commit)-[:MODIFIES]->(db) }

WITH bt,
     (pText IS NOT NULL) AS byText,
     (pImg  IS NOT NULL) AS byImage
RETURN count(bt)                                             AS totalTerms,
       count(CASE WHEN byText OR byImage THEN 1 END)         AS matched,
       count(CASE WHEN byImage AND NOT byText THEN 1 END)    AS imageOnly,
       round(100.0 * count(CASE WHEN byText OR byImage THEN 1 END) / count(bt), 1) AS matchRatePct,
       collect(CASE WHEN NOT (byText OR byImage) THEN bt.term END)[..20] AS unmatchedSample;

마지막 unmatchedSample이 실무에서 가장 자주 쓰인다. 매칭률 숫자보다 “무엇이 매칭 안 됐는지”가 개선 액션을 만든다.
