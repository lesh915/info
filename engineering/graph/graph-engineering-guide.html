그래프 엔지니어링이란 무엇인가

그래프 엔지니어링(Graph Engineering)은 여러 개의 에이전트·도구·단계를 노드(node)와 엣지(edge)로 이루어진 명시적 제어 흐름 위에서 조율하는 오케스트레이션 설계 방식을 가리키는 용어다. TrueFoundry의 실무 정의에 따르면, 그래프 엔지니어링은 런타임 작업 그래프(work graph)가 어떻게 형성되고 변화하는지를 다루는 반면, 루프 엔지니어링은 개별 에이전트 노드 하나가 내부적으로 어떻게 실행되는지를 다룬다는 점에서 서로 다른 추상화 층위에 위치한다.[1]

용어의 등장 배경

"그래프 엔지니어링"은 완전히 새로운 개념이라기보다, 2026년 중반 소셜미디어(X)에서 벌어진 용어 논쟁을 통해 대중화된 표현이다. 이보다 몇 주 앞서, Claude Code를 개발한 Anthropic의 Boris Cherny와 OpenClaw 제작자 Peter Steinberger가 "더 이상 프롬프트를 작성하지 않고, 프롬프트를 생성하는 루프를 설계한다"는 취지의 발언을 하면서 루프 엔지니어링이라는 표현이 AI 엔지니어링 커뮤니티에서 지배적인 용어로 자리잡았다. 이후 여러 에이전트가 서로 어떻게 조율되는지를 설명하기 위한 후속 용어로 그래프 엔지니어링이 등장했다.[21]

2026년 7월, Andrew Ng의 지식그래프 강좌 발표와 Linear의 자율 반복 실행 기능 "Loops" 출시가 겹치면서 X에서 "에이전트 오케스트레이션은 그래프인가, 루프인가"라는 논쟁이 재점화되었다. 이 논쟁에서 LangChain 창립자 Harrison Chase는 "그래프 엔지니어링이 정확히 무엇인지는 잘 모르겠지만, 결국 LangGraph를 가리키는 것 같다"는 취지로 반응했으며, 이 발언은 실제로 많은 개발자들이 두 개념(지식그래프 데이터 구조와 LangGraph 오케스트레이션 프레임워크)을 혼동하고 있었음을 보여준다.[2]

용어 정리 — 두 개의 서로 다른 "그래프" 본 문서가 다루는 그래프 엔지니어링(오케스트레이션)은 에이전트·도구·단계 간의 실행 순서와 제어 흐름을 그래프로 모델링하는 것을 말한다. 이는 사용자가 별도로 다루고 있는 지식그래프/온톨로지(Neo4j 기반 데이터 구조)와는 노드·엣지라는 용어만 공유할 뿐, 서로 다른 개념이다. 설명 확인 출처.[2]

비판적 관점 — "재브랜딩"이라는 시각

객관성을 위해 반대 의견도 함께 정리한다. AI Builder Club과 Louis Bouchard의 분석은 공통적으로, 그래프 형태의 오케스트레이션 자체는 전혀 새로운 것이 아니라고 지적한다. State-machine 및 그래프 오케스트레이션은 LangGraph, Microsoft AutoGen, Google ADK 등에서 이미 오래전부터 구현되어 있었으며, 더 거슬러 올라가면 Airflow와 같은 DAG 기반 워크플로 엔진, 그리고 Anthropic이 2024년 말 공개한 Building Effective Agents 글에서 이미 체이닝·라우팅·병렬화·오케스트레이터-워커·평가자-최적화자라는 다섯 가지 패턴으로 정리된 바 있다. 즉 2026년 7월에 새로워진 것은 아키텍처 자체가 아니라 어휘(vocabulary)라는 것이 이들의 결론이다.[6][3]

반대로 실무 옹호 진영(TrueFoundry, Eigent)은 이 용어가 최소한 실무에서 유용한 구분을 제공한다고 본다 — 즉 "에이전트 하나의 실행 루프를 어떻게 안정화할 것인가"라는 문제와 "여러 루프를 어떻게 병렬화·거버넌스·감사할 것인가"라는 문제는 실제로 서로 다른 엔지니어링 관심사이며, 이를 구분해서 부르는 것 자체가 실익이 있다는 입장이다.[1][4]

이 가이드는 "그래프 엔지니어링"을 하나의 확정된 표준 용어가 아니라, 실무에서 관찰되는 아키텍처 패턴에 최근 붙여진 이름으로 취급하며, 패턴 자체의 기술적 실체(LangGraph 등 프레임워크가 실제로 구현하고 있는 것)에 초점을 맞춘다.

배경 지식 — 루프 엔지니어링과 ReAct 패턴

그래프 엔지니어링을 이해하려면 먼저 그것이 조율하는 대상, 즉 개별 에이전트의 실행 단위인 에이전트 루프(agent loop)를 이해해야 한다. 에이전트 루프란 LLM이 반복적으로 (1) 추론하고 (2) 행동(도구 호출)하고 (3) 결과를 관찰한 뒤 다음 행동을 결정하는 반복 구조를 말한다. 가장 단순한 형태로는 while 루프 안에서 LLM이 도구를 호출하는 구조에 불과하다.[8]

ReAct: Thought → Action → Observation

이 패턴을 정식화한 것이 2022년 Yao 등이 제안한 ReAct(Reasoning + Acting) 프레임워크다. ReAct는 추론(Thought)과 행동(Action)을 별도 단계로 분리하지 않고 하나의 반복 사이클 안에서 교차시킨다. 매 사이클마다 모델은 현재 상태를 해석하는 Thought를 생성하고, 도구를 호출하는 Action을 선택하며, 그 결과인 Observation을 다시 컨텍스트에 반영해 다음 추론에 활용한다.[12][9]

ReAct는 현재 대부분의 프로덕션 에이전트(LangChain의 AgentExecutor, 다수의 코딩 에이전트 등)에서 기본 오케스트레이션 패턴으로 채택되어 있으며, 루프 엔지니어링 작업의 출발점으로 간주된다.[14] ReAct 이후 등장한 변형 패턴으로는 Plan-and-Execute(사전 계획 후 실행), ReWOO(추론과 관찰의 분리로 토큰 비용 절감), Reflexion(실패 후 자기 비평을 메모리에 저장해 재시도에 반영)이 있다.[11]

단일 루프의 알려진 실패 모드

실패 모드설명
무한 루프 (Infinite loop)목표에 대한 명확한 검증 기준이 없어 에이전트가 끝없이 "개선"을 시도함. 2023년 AutoGPT 사례가 대표적으로 언급됨.
목표 표류 (Goal drift)모호한 지시나 예상치 못한 도구 결과에 이끌려 관련은 있으나 다른 목표를 추구하게 됨.
컨텍스트 오버플로우장시간 세션에서 컨텍스트 윈도우가 가득 차 추론 품질이 저하됨.
침묵 실패 (Silent failure)실제 진전이 없음에도 확신에 찬 출력을 생성함.

출처: [14]

핵심 요약 루프 엔지니어링은 단일 에이전트가 자신의 목표를 향해 안정적으로 수렴하도록 만드는 작업이다 — 검증기(verifier), 정지 조건, 컨텍스트 관리가 핵심 관심사다. 그래프 엔지니어링은 이런 루프 "여러 개"를 어떻게 배치·연결·감시할지를 다루는, 그 위층의 작업이다.

루프 엔지니어링 vs 그래프 엔지니어링

AI Builder Club의 정의가 실무적으로 명확하다: 그래프 엔지니어링은 루프 위에 얹히는 오케스트레이터 레이어다. 하나의 노드가 자기 자신을 향해 되돌아가는 엣지를 가지면 그것은 루프이고, 여러 개의 전문화된 노드와 라우팅이 추가되면 그래프가 된다.[7]

그래프 엔지니어링 아키텍처

4.1 원형(prototype) 패턴 — Anthropic의 5가지 워크플로 패턴

Anthropic이 2024년 12월 공개한 엔지니어링 블로그 Building Effective Agents는 그래프 엔지니어링 논쟁에서 가장 자주 인용되는 선행 사례다. 이 글은 워크플로(사전에 정의된 코드 경로를 따르는 시스템)와 에이전트(모델이 스스로 프로세스와 도구 사용을 통제하는 시스템)를 구분하고, 다섯 가지 조합 가능한 워크플로 패턴을 제시한다.[34]

패턴 1

프롬프트 체이닝

작업을 순차적 LLM 호출로 분해하고, 각 단계 사이에 프로그래밍적 점검을 둔다. 번역, 문서 생성처럼 단계가 예측 가능한 저복잡도 작업에 적합.
패턴 2

라우팅

입력을 분류해 전문화된 하위 프롬프트로 분기한다. 카테고리가 명확한 고객 문의 처리 등에 적합.
패턴 3

병렬화

독립적인 하위 작업을 동시 실행(sectioning)하거나, 동일 작업을 여러 번 실행해 합의를 구한다(voting).
패턴 4

오케스트레이터-워커

중앙 LLM이 실행 시점에 작업을 동적으로 분해해 워커에게 위임하고 결과를 종합한다. 하위 작업을 사전에 예측할 수 없는 코딩·리서치 작업에 적합.
패턴 5

평가자-최적화자

한 LLM이 생성하고 다른 LLM이 평가·피드백하는 루프를 반복한다. 명확한 평가 기준이 있고 반복 개선이 유의미한 가치를 낼 때 효과적.
공통 원칙

단순함이 이긴다

Anthropic은 "가장 성공적인 구현은 복잡한 프레임워크가 아니라 단순하고 조합 가능한 패턴을 사용한다"고 명시적으로 결론짓는다.[34]

이 다섯 패턴을 화이트보드에 그리면 곧 그래프가 된다는 것이 비판적 관점의 핵심 논거다 — 즉 그래프 엔지니어링이 다루는 실체는 이미 2024년에 이름을 갖고 있었다는 것이다.[3]

4.2 작업 그래프와 4계층 루프 구조

Eigent의 정리에 따르면, 에이전트 그래프에는 개념적으로 두 층위가 있다. 작업/태스크 그래프(work graph)는 에이전트가 "무엇을" 하는지를 나타내며 노드는 도구·스킬·파일·하위 작업이다. 그 위에, 그래프 기반 에이전트 플랫폼은 통상 네 종류의 감시 루프를 층위별로 둔다.[4]

루프 종류관심사
운영 루프 (Operational)작업별 성공률, 지연시간, 비용, 리소스 사용량
품질 루프 (Quality)사람 또는 자동 평가 점수, 오류율, 안전성 검사
거버넌스 루프 (Governance)목표치를 누가 설정하고, 누가 임계값을 조정할 수 있으며, 언제 변경을 배포하는지
감사 루프 (Audit)지표가 여전히 실제 비즈니스 성과와 상관관계를 갖는지 주기적으로 점검

출처.[4]

4.3 멀티에이전트 토폴로지 개관

여러 에이전트를 그래프로 조율하는 방식은 크게 세 가지 토폴로지로 수렴한다 — 라우터, 슈퍼바이저, 스웜. 각각의 구현은 5절에서 코드와 함께 다룬다.

토폴로지제어 방식특징
라우터 (Router)단일 분류 단계가 입력을 분석해 정적으로 디스패치대화 이력을 유지하지 않는 전처리 단계. 입력 카테고리가 명확할 때 적합.[20]
슈퍼바이저 (Supervisor)중앙 에이전트가 매 턴마다 어떤 워커를 호출할지 동적으로 결정전체 메시지 이력을 누적하므로 8~12회 왕복 이후 라우팅 정확도가 저하되는 경향이 보고됨.[19]
스웜 (Swarm)중앙 조정자 없이 에이전트가 핸드오프 도구를 통해 서로 직접 제어를 이전마지막으로 활성화된 에이전트를 기억해 다음 상호작용에서 이어감.[23]

LangGraph 기반 개발 가이드

LangGraph는 LangChain Inc.가 2024년 공개한 오픈소스 Python/TypeScript 프레임워크로, 상태를 가진(stateful) 순환 그래프(cyclic directed graph)로 에이전트 워크플로를 모델링한다. 실무에서 "그래프 엔지니어링"이 지시하는 대상은 사실상 대부분 LangGraph의 실행 모델을 가리킨다는 것이 Harrison Chase의 논평에서도 확인된다.[2] LangChain이 컴포넌트(프롬프트, 파서, RAG 파이프라인)를 조립하는 라이브러리라면, LangGraph는 그 컴포넌트들이 상태를 가진 순환 워크플로에 참여할 때 사용하는 더 저수준의 실행 엔진이다. 2026년 기준 LangChain의 에이전트 추상화 자체도 LangGraph 런타임 위에서 동작한다.[13]

5.1 핵심 프리미티브

State

공유 상태

TypedDict 또는 Pydantic 모델로 정의되는, 모든 노드가 읽고 갱신하는 공유 객체. 특정 실행 전체에 걸친 에이전트의 지속 메모리 역할을 한다.[13]
Node

노드

현재 상태를 받아 상태에 대한 부분 갱신을 반환하는 Python 함수. LangChain Runnable이나 컴파일된 서브그래프도 노드가 될 수 있다.[17]
Edge

엣지

노드 간 전이. 무조건 엣지(A 다음 항상 B)와 조건부 엣지(라우팅 함수 결과에 따라 다음 노드를 선택)가 있으며, 조건부 엣지가 분기를 구현하는 방식이다.[17]
Reducer

리듀서

여러 노드의 갱신을 하나의 상태 필드로 병합하는 규칙. 기본값은 "마지막 쓰기가 이긴다"이며, 메시지 목록처럼 누적이 필요한 필드는 concat 리듀서를 지정한다.[17]

Example 1 — 최소 StateGraph 정의

from typing import TypedDict
from langgraph.graph import StateGraph, END

class TaskState(TypedDict):
    request: str
    draft: str
    approved: bool

def draft_node(state: TaskState) -> dict:
    # LLM 호출로 초안 생성
    return {"draft": llm_generate(state["request"])}

def review_node(state: TaskState) -> dict:
    # 별도 LLM 호출로 초안 검토
    ok = llm_review(state["draft"])
    return {"approved": ok}

def route_after_review(state: TaskState) -> str:
    return "publish" if state["approved"] else "draft"

graph = StateGraph(TaskState)
graph.add_node("draft", draft_node)
graph.add_node("review", review_node)
graph.set_entry_point("draft")
graph.add_edge("draft", "review")
graph.add_conditional_edges(
    "review", route_after_review,
    {"publish": END, "draft": "draft"},
)

app = graph.compile()
result = app.invoke({"request": "분기 릴리스 노트 작성"})

위 review → draft 조건부 엣지는 "그래프 안에 내장된 평가자-최적화자 루프"에 해당한다 — 즉 그래프 엔지니어링과 루프 엔지니어링이 배타적이지 않고, 그래프의 노드 하나가 자기 자신에게 되돌아가는 순환을 갖는 것이 정확히 4.1의 패턴 5(평가자-최적화자)를 구현하는 방식이다.[34]

5.2 상태 누적과 리듀서 — 대화형 에이전트 루프

도구를 반복 호출하는 ReAct 스타일 루프를 그래프 안에서 표현할 때는, 메시지가 누적되는 필드에 리듀서를 지정하고 "도구 호출이 남아있는가"를 조건부 엣지의 판단 기준으로 사용한다.

Example 2 — 그래프로 구현한 ReAct 루프

from typing import Annotated, TypedDict
from operator import add
from langgraph.graph import StateGraph, END

class AgentState(TypedDict):
    messages: Annotated[list, add]   # 누적 리듀서

def agent_node(state: AgentState) -> dict:
    response = llm_with_tools.invoke(state["messages"])
    return {"messages": [response]}

def tool_node(state: AgentState) -> dict:
    last = state["messages"][-1]
    results = execute_tool_calls(last.tool_calls)
    return {"messages": results}

def should_continue(state: AgentState) -> str:
    last = state["messages"][-1]
    return "tools" if getattr(last, "tool_calls", None) else "end"

graph = StateGraph(AgentState)
graph.add_node("agent", agent_node)
graph.add_node("tools", tool_node)
graph.set_entry_point("agent")
graph.add_conditional_edges("agent", should_continue, {"tools": "tools", "end": END})
graph.add_edge("tools", "agent")   # ReAct의 Observation → 다음 Thought

app = graph.compile()

5.3 체크포인터와 영속성

컴파일된 그래프는 동기 호출(invoke), 스트리밍(stream), 사람의 개입을 위한 중단(interrupt), 그리고 모든 스텝에서의 체크포인트 저장을 지원한다.[13] LangChain의 2026년 에이전트 엔지니어링 현황 보고서는 프로덕션 인시던트의 60% 이상이 상태 관리 문제와 관련되어 있다고 밝혔는데, 체크포인터는 이 문제에 대응하는 핵심 장치다.[16]

Example 3 — 스레드 기반 영속성과 사람 개입(interrupt)

from langgraph.checkpoint.memory import InMemorySaver
# 프로덕션에서는 Postgres/Redis 등 영속 백엔드 사용

checkpointer = InMemorySaver()
app = graph.compile(checkpointer=checkpointer, interrupt_before=["review"])

config = {"configurable": {"thread_id": "case-2026-0823"}}
app.invoke({"request": "..."}, config=config)

# review 노드 직전에서 실행이 정지된다.
# 사람이 상태를 확인/수정한 뒤 동일 thread_id로 재개:
app.invoke(None, config=config)

같은 thread_id로 다시 호출하면 중단된 지점부터 정확히 재개되며, 이는 LangGraph가 "interrupt-and-resume을 1급 시민(first-class primitive)으로 취급한다"는 특징에서 비롯한다.[14]

5.4 서브그래프를 통한 컨텍스트 격리

슈퍼바이저 패턴에서 전체 메시지 이력이 누적되면 라우팅 정확도가 저하되는 문제가 보고된다. LangGraph는 컴파일된 그래프 전체를 부모 그래프의 노드로 중첩(nested subgraph)할 수 있게 하여, 팀 단위로 상태를 격리한다.[19]

research_team = research_graph.compile()   # 독립적으로 컴파일된 서브그래프

parent = StateGraph(ParentState)
parent.add_node("research_team", research_team)   # 서브그래프를 노드로 사용
parent.add_node("writer", writer_node)
parent.add_edge("research_team", "writer")

토폴로지 구현: Supervisor · Swarm · Router

6.1 슈퍼바이저 패턴

슈퍼바이저는 모든 요청을 받아 어떤 워커를 호출할지 결정하고, 결과를 읽은 뒤 계속할지 종료할지 판단하는 중앙 오케스트레이터다.[25]

from langgraph.graph import StateGraph, END
from langgraph.prebuilt import create_react_agent

billing_agent = create_react_agent(llm, tools=billing_tools)
tech_agent = create_react_agent(llm, tools=tech_tools)

def supervisor_node(state: SupState) -> dict:
    decision = supervisor_llm.invoke(state["messages"])
    return {"next": decision.next_worker}   # "billing" | "tech" | "done"

def route(state: SupState) -> str:
    return state["next"]

graph = StateGraph(SupState)
graph.add_node("supervisor", supervisor_node)
graph.add_node("billing", billing_agent)
graph.add_node("tech", tech_agent)
graph.set_entry_point("supervisor")
graph.add_conditional_edges("supervisor", route,
    {"billing": "billing", "tech": "tech", "done": END})
graph.add_edge("billing", "supervisor")
graph.add_edge("tech", "supervisor")

6.2 스웜 패턴 — Command 기반 핸드오프

스웜은 중앙 조정자 없이 에이전트가 핸드오프 도구를 호출해 서로 직접 제어를 이전한다. 핸드오프 도구는 Command(goto=..., graph=Command.PARENT)를 반환하여 부모 그래프의 상태를 갱신하며 다음 노드로 이동시킨다.[28]

from langgraph.types import Command
from langchain_core.tools import tool

@tool
def handoff_to_tech(reason: str) -> Command:
    """기술 지원이 필요할 때 기술 에이전트로 전환한다."""
    return Command(
        goto="tech_agent",
        graph=Command.PARENT,
        update={"handoff_reason": reason},
    )

마지막으로 활성화된 에이전트를 시스템이 기억하기 때문에, 다음 사용자 메시지가 들어오면 그 에이전트부터 대화가 재개된다.[27]

6.3 라우터 패턴 — Send를 이용한 병렬 팬아웃

라우터는 입력을 분류해 정적으로 디스패치하는 전처리 단계로, 대화 이력을 유지하지 않는다. Send API를 사용하면 분류 결과에 따라 여러 전문 에이전트로 동시에 팬아웃할 수 있다.[20]

from langgraph.types import Send

def route_query(state: State) -> list[Send]:
    classifications = classify_query(state["query"])
    return [Send(c["agent"], {"query": c["query"]}) for c in classifications]

graph.add_conditional_edges("classify", route_query)
선택 기준 라우터는 입력 카테고리가 명확하고 결정적 디스패치로 충분할 때. 슈퍼바이저는 대화가 여러 턴에 걸쳐 진화하며 LLM이 문맥에 따라 다음 행동을 유연하게 결정해야 할 때. 스웜은 중앙 병목 없이 대등한 에이전트 간 직접 전환이 필요할 때 적합하다.[20]

선택 프레임워크와 안티패턴

루프에서 그래프로 넘어가야 하는 신호

AI Builder Club의 마이그레이션 가이드는 "루프로 시작해서, 필요해질 때만 그래프로 승격하라"는 원칙을 제시한다. 다음 네 가지 질문이 실무에서 반복적으로 사용되는 결정 기준이다.[5][22]

  1. 서로 다른 역할(리뷰어, 병렬 조사자, 거부권을 가진 검사자)이 필요한가?
  2. 일부 단계를 병렬로 실행해 지연시간을 줄일 필요가 있는가?
  3. 한 노드가 다른 노드의 컨텍스트를 오염시키지 않도록 격리가 필요한가?
  4. 각 노드가 다음 노드에 정확히 무엇을 넘기는지 명확히 정의할 수 있는가? (정의할 수 없다면 아직 분리할 준비가 되지 않은 것)
안티패턴 경고 "밈에 대응한다고 40개짜리 에이전트 그래프를 밤새 돌리지 말 것." 과도하게 큰 그래프는 토큰 예산만 소모하고 실질적 진전은 거의 만들어내지 못하는 경우가 많다. 권장되는 접근은 검증 가능한 단일 반복 작업 하나에서 시작해, 상태를 눈으로 확인할 수 있는 UI와 지표를 갖추고, 실패 양상을 충분히 이해한 뒤에만 리뷰어·병렬 분기·거부권을 가진 보안 검사 등을 추가해 그래프로 성장시키는 것이다.[3]

Anthropic의 워크플로 vs 에이전트 선택 기준 (참고)

복잡도권장 패턴
낮음 — 단계가 예측 가능워크플로 (체이닝 / 라우팅)
중간 — 하위 작업이 실행 시점에 결정됨오케스트레이터-워커
높음 — 서로 다른 전문성이 필요멀티에이전트 시스템

출처.[39]

공통된 결론 본 가이드가 검토한 모든 출처가 동의하는 지점은 하나다 — 아키텍처 선택은 유행하는 용어가 아니라 실제 문제의 구조(병렬성 필요 여부, 역할 분리 필요 여부, 검증 가능성)에 의해 결정되어야 한다는 것이다. "그래프 엔지니어링"이라는 이름 자체보다, LangGraph 등의 프레임워크가 실제로 제공하는 상태 관리·체크포인팅·조건부 라우팅이라는 구체적 도구가 문제 해결의 실체다.
