ReAct 패밀리 10패턴을 LangGraph로 직접 만든다

앞선 두 문서에서 정리한 ReAct, Plan-and-Execute, ReWOO, Reflexion, LATS(핵심 5패턴)와 Tree of Thoughts, Self-Ask, ADaPT, CodeAct, Voyager형 스킬 라이브러리(확장 5패턴)를 LangGraph 1.2.x(2026년 8월 기준 최신) API로 직접 구현한다. 각 패턴마다 아키텍처, 상태 스키마, 순서도, 그리고 실제로 실행 가능한 파이썬 코드를 담았다.

중요한 전제 하나: LangGraph는 2025년 하반기부터 langgraph.prebuilt.create_react_agent를 langchain.agents.create_agent로 대체하기 시작했고, ReWOO·Reflexion·LATS·Tree of Thoughts의 공식 튜토리얼 페이지는 문서 사이트 개편 과정에서 실제로 내려갔다. 이 가이드는 각 패턴마다 "지금도 공식 유지 중인지, 과거 커밋에서 복원한 것인지, 커뮤니티 공식 라이브러리인지, 직접 설계한 것인지"를 명확한 배지로 표시한다 — 실제 코드베이스에 붙일 때 무엇을 검증해야 하는지 알 수 있도록.

← 각 패턴의 이론적 배경은 「ReAct 패밀리」·「ReAct 확장편」 문서 참고

공통 주의사항

거의 모든 패턴에 해당

  • recursion_limit(기본 25)은 루프가 도는 안전장치일 뿐, 값을 무작정 올리는 게 해법이 아니다 — 걸린다는 것 자체가 종료 조건 설계 결함의 신호다.
  • 여러 병렬 브랜치가 같은 상태 키에 쓸 때는 Annotated[dict, operator.or_] 같은 병합 리듀서가 필수다. 없으면 마지막 쓰기만 남거나 충돌 에러가 난다.
  • model.with_structured_output(PydanticModel)은 "깔끔한 타입 객체"가 필요할 때, bind_tools(...)+파서는 "ToolNode가 소비할 tool_call이 달린 메시지"가 필요할 때 — 둘을 섞어 쓰면 그래프 배선이 꼬인다.
  • langchain_community.tools.tavily_search.TavilySearchResults는 deprecated — langchain_tavily.TavilySearch로 교체.

모델 ID에 대한 안내

  • 이 문서의 코드에 등장하는 모델 문자열(gpt-4o, claude-sonnet-... 등)은 예시다.
  • 모델 제공사는 스냅샷을 주기적으로 갱신하므로, 실제 배포 전 각 제공사 문서에서 현재 유효한 모델 ID를 반드시 다시 확인할 것.
  • 가능하면 langchain.chat_models.init_chat_model("provider:model") 같은 provider-agnostic 생성자를 쓰면 모델 교체가 한 줄로 끝난다.

rewoo.pypython

구현 시 주의할 점

  • 병렬 브랜치가 함께 쓰는 results는 반드시 Annotated[dict, operator.or_]로 병합 리듀서를 선언한다.

LATS

보관됨 → 전면 현대화 공식 튜토리얼 페이지는 리다이렉트됨 — 레거시 API(pydantic_v1, ToolExecutor 등) 전면 교체

LangGraph는 트리 자체를 상태 스키마로 감당하지 않는다 — TreeState는 root·selected 같은 참조만 들고 있고, 실제 부모/자식 링크, 방문 횟수, UCT 계산은 평범한 파이썬 Node 클래스가 담당한다. "LangGraph는 바깥 루프만, 트리는 순수 Python이 소유"하는 이 분리가 현재도 권장되는 접근이다.

lats.pypython

레거시 → 현재 API 교체 목록

  • langchain_core.pydantic_v1 → 순정 pydantic(v2)
  • ToolExecutor/ToolInvocation → 도구를 직접 .invoke() 하거나 ToolNode 사용
  • llm.generate(n=N)(일부 제공사 전용) → Send 기반 병렬 팬아웃

탐색 관련 주의

  • 트리 변형(자식 추가 등)은 반드시 backpropagate 안에서 직렬로만 수행 — 병렬 브랜치가 공유 트리를 동시에 건드리면 경쟁 상태가 생긴다.
  • recursion_limit 기본 25는 반복 탐색에 턱없이 부족 — 50~100 이상 지정.

확장 패턴 1 · 순수 추론 탐색

Tree of Thoughts

직접 재구성 공식 노트북 원문 복구 불가(문서 이관으로 소실) — 논문 알고리즘 기준 24게임으로 재작성

prune상위 b개만 남겨 다음 프론티어로
↺ 해를 찾거나 깊이 한도에 닿을 때까지 expand로 복귀 — LATS와 달리 UCT·역전파 없음

LATS가 MCTS(UCT+역전파)라면, ToT는 너비 제한 BFS다 — 매 깊이마다 프론티어 전체를 한 번에 확장하고, 평가 점수로 정렬해 상위 b개만 남긴다. 24게임에서 4·9·10·13 같은 네 숫자로 24를 만드는 문제를 예시로 삼았다. LLM의 산술 계산은 신뢰하지 않고, 연산 결과와 "정확히 24인가"는 파이썬으로 결정적으로 재계산한다 — 검증 가능한 것을 LLM 판단에 맡기지 않는다.

Self-Ask

직접 설계 2022년 프롬프팅 기법 — LangGraph 참조 구현 자체가 존재하지 않음
reason후속질문 필요? + (필요시) 다음 질문
need_followup & hop < MAX?
search_followup검색 실행 → (질문,답) 누적
↺ search_followup → reason 반복, 아니면 finish로 최종 답

원 논문의 "Are follow up questions needed here:" 판단과 "Follow up: ..." 질문 생성을 구조화 출력 하나로 합쳤다(토큰 효율↑). hop 카운터가 의미 있는 종료 장치이고, recursion_limit은 그보다 넉넉한 값으로 잡아 둘째 안전장치로만 쓴다.

ADaPT

직접 설계 논문 Algorithm 1(ADAPT(Task, depth))을 명시적 스택으로 펼쳐 LangGraph에 맞춤
execute_task스택 top이 task면 실행 시도
성공 / 실패+depth 초과 / 실패+분해 가능
성공 → 결과 기록
실패+한도 → 포기(False)
실패 → join+자식 task를 스택에 push(LIFO)
↺ join 프레임은 자식이 모두 해소된 뒤 AND/OR로 결합, 스택이 빌 때까지 반복

LangGraph는 그래프가 자기 자신을 임의 깊이로 호출하는 진짜 재귀에 최적화돼 있지 않다. 그래서 재귀 호출 스택을 명시적 LIFO 스택으로 펼쳤다 — join 프레임을 자식 task 프레임들보다 먼저 push해두면, LIFO 팝 순서가 자동으로 "자식이 모두 끝난 뒤 부모를 합친다"는 후위 순회를 보장한다. depth >= max_depth에서 그대로 포기(False)하는 것도 원 논문의 if k > dmax: return False를 그대로 따른 것이다 — 강제로 직접 실행시키는 폴백은 없다.

adapt.pypython
대안 설계도 있다. 노드 함수가 컴파일된 그래프 자신을 런타임에 .invoke()해서 진짜 자기재귀를 흉내내는 방법도 가능하다 — Algorithm 1과 더 직접적으로 대응되지만, 재귀 호출마다 독립된 Pregel 실행이 시작돼 바깥쪽 실행의 recursion_limit·체크포인터·stream()이 안쪽까지 보이지 않는다는 단점이 있다. 관측 가능성이 중요한 디버깅 단계에서는 위 스택 방식을 권장한다.

확장 패턴 4 · 행동 자체를 코드로

CodeAct

커뮤니티 공식 langchain-ai/langgraph-codeact — langchain-ai 조직이 직접 유지하는 별도 pip 패키지
call_model시스템 프롬프트에 도구를 함수 스텁으로 노출, 코드블록 생성
코드블록 있음?
sandboxcontext(누적 변수+도구)와 함께 exec, 새 변수 병합
↺ sandbox → call_model 반복, 코드 없이 텍스트만 응답하면 종료

도구가 JSON tool_call이 아니라 시스템 프롬프트에 함수 스텁으로 노출되고, 모델은 result = add(2, 3)처럼 실제 파이썬 코드를 작성한다. 실행 결과(stdout)는 user 역할 메시지로 되돌아가 다음 턴의 관찰이 되고, 코드에서 정의한 최상위 변수는 context에 누적돼 다음 코드 블록에서 그대로 참조할 수 있다 — CodeAct 논문이 강조하는 "지속되는 인터프리터 상태"다.

codeact_example.pypython · langgraph-codeact 공식 예제
샌드박스 보안 주의. 위 eval() 함수는 순정 exec()를 사용한다 — 학습·데모용이며 신뢰할 수 없는 코드나 프로덕션에는 절대 그대로 쓰면 안 된다. 한때 권장되던 langchain_experimental.PythonREPL은 더 이상 유지되지 않고, 그 대안이던 langchain-sandbox(Pyodide 기반)도 2026년 1월에 아카이브됐다. 실제 배포에서는 컨테이너·gVisor·Firecracker·E2B 같은 별도 격리 샌드박스에서 eval_fn을 실행하도록 교체할 것.

확장 패턴 5 · 영구 스킬 라이브러리

Voyager형 스킬 라이브러리 에이전트

직접 설계 공식 langgraph-voyager 패키지는 존재하지 않음 — 마인크래프트 특화 논문을 범용 에이전트로 일반화
propose_goal커리큘럼: 다음 하위 목표 제안
retrieve_skillsStore에서 관련 스킬 의미검색
generate_code스킬 재사용하며 코드 작성
execute → verify샌드박스 실행 후 자기검증
↺ 성공 시 save_skill로 Store에 영구 저장 후 propose_goal로, 실패 시 재시도 또는 포기

Reflexion의 메모리가 "이번 시도가 왜 실패했나"를 담은 휘발성 반성문이라면, Voyager형 메모리는 성공한 코드 자체를 이름 붙여 영구 저장한다. LangGraph의 체크포인터 (InMemorySaver, 세션 내 단기 상태)와 스토어(InMemoryStore, 스레드를 넘나드는 장기 저장소)는 정확히 이 두 층위에 대응한다 — 스킬 라이브러리는 스토어의 의미 검색 인덱스에 {설명, 코드}로 저장하고, 다음 작업에서 store.search()로 관련 스킬을 불러와 조합한다.

voyager_style_agent.pypython

이 설계의 핵심 선택

  • 단기 상태(진행 중인 시도)는 체크포인터, 장기 지식(스킬)은 스토어 — LangGraph 기본 API 두 가지로 Voyager의 두 메모리 층위를 그대로 표현했다.
  • Runtime[AgentContext]를 노드의 두 번째 인자로 받아 runtime.store·runtime.context에 접근하는 것이 현재 권장되는 방식이다(예전의 config+ get_store() 방식 대체).

실전 적용 시 교체할 부분

  • 예제의 fake_embed는 외부 API 없이 돌아가게 한 더미 — 실제로는 init_embeddings("openai:text-embedding-3-small") 등 진짜 임베딩으로 교체.
  • 영속성이 세션을 넘어 실제로 유지돼야 한다면 InMemoryStore/ InMemorySaver를 PostgresStore/ PostgresSaver로 교체.

마무리

배포 전 체크리스트

  1. recursion_limit을 패턴별로 명시했는가. 기본값 25는 ReAct 정도에만 적당하고, Plan-and-Execute·LATS·ADaPT처럼 여러 서브루프가 겹치는 패턴은 50~100 이상 필요하다.
  2. 병렬 브랜치가 쓰는 상태 키에 병합 리듀서를 선언했는가. (operator.add, operator.or_, 또는 직접 작성한 병합 함수)
  3. deprecated API를 걷어냈는가. create_react_agent→create_agent, TavilySearchResults→TavilySearch, pydantic_v1→pydantic, ToolExecutor→직접 invoke/ToolNode.
  4. 구조화 출력과 tool-call 방식을 목적에 맞게 골랐는가. 타입 객체만 필요하면 with_structured_output, ToolNode가 소비해야 하면 bind_tools+파서.
  5. 모델 ID를 하드코딩하지 않았는가. 제공사 문서에서 현재 유효한 스냅샷을 확인하거나 init_chat_model로 provider-agnostic하게 구성.
  6. 샌드박스가 신뢰할 수 없는 코드를 실행하는 경우, 실제 격리 환경으로 교체했는가. (CodeAct·Voyager형 패턴의 exec() 예제는 데모 전용)
  7. 장기 실행 에이전트라면 체크포인터/스토어를 인메모리에서 영속 백엔드로 바꿨는가. (SqliteSaver/PostgresSaver, PostgresStore 등)
