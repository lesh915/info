Graph Engineering / Implementation Guide

LangGraph 기반 그래프 엔지니어링
단계별 개발 가이드

요구사항 분석부터 배포·운영까지, 그래프 오케스트레이션 에이전트를 실제로 구축하는 10단계 개발 파이프라인을 코드와 함께 정리한다. 앞서 작성한 graph-engineering-guide.html의 개념적 논의를 실전 구현 단계로 확장한 별도 문서다.

전제 문서 그래프 엔지니어링 상세 가이드 (개념/비교) 대상 프레임워크 LangGraph (Python) 기준 시점 2026년 8월
00 준비 01 설계 02 State 03 노드 04 엣지/라우팅 05 컴파일/테스트 06 영속성/HITL 07 내결함성 08 멀티에이전트 확장 09 관찰가능성/평가 10 배포/운영 참고문헌

이 가이드는 LangGraph로 그래프 엔지니어링 기반 에이전트를 만드는 과정을 11개 단계(00~10)로 나누어 정리한다. 각 단계는 실제 개발 순서를 따르며, 앞 단계의 산출물이 다음 단계의 입력이 되도록 구성했다. 작은 단일 루프에서 시작해 필요할 때만 그래프로 확장한다는 원칙에 따라, 06~08단계(영속성/내결함성/멀티에이전트 확장)는 실제로 그 복잡도가 필요해졌을 때 적용하는 단계로 표시했다.

01

요구사항 분석과 그래프 설계

Work-Graph Design
목표노드·엣지 후보를 화이트보드 수준에서 확정
산출물노드 목록, 전이 조건, 종료 조건이 적힌 설계 문서

코드를 쓰기 전에 세 가지 질문에 먼저 답한다. 이는 앞선 개념 문서(§7)에서 정리한 "루프 → 그래프 승격 신호"를 설계 체크리스트로 구체화한 것이다.[1]

  1. 노드 식별 — 이 작업은 몇 개의 서로 다른 "역할"로 나뉘는가? (예: 초안 작성자, 검토자, 도구 실행자)
  2. 전이 조건 식별 — 각 노드에서 다음으로 어떤 조건에서 어떤 노드로 가는가? 조건이 결정적(deterministic)인가, LLM이 판단해야 하는가?
  3. 종료 조건 식별 — 언제 그래프가 끝나는가? 무한 루프를 막을 최대 반복 횟수 또는 명시적 검증 기준이 있는가?
설계 원칙 — 단순하게 시작 Anthropic의 워크플로 패턴 연구는 "가장 성공적인 구현은 복잡한 프레임워크가 아니라 단순하고 조합 가능한 패턴을 사용한다"고 강조한다. 처음부터 멀티에이전트 그래프(08단계)를 설계하지 말고, 먼저 단일 에이전트 + 도구 루프(체이닝 또는 라우팅 수준)로 노드 3~5개 이내에서 시작할 것을 권장한다.[20]

설계 산출물 예시 — 초안-검토 워크플로

노드역할다음 전이
draft사용자 요청으로 초안 생성항상 → review
review초안 품질 평가승인 → END / 반려 → draft (최대 3회)

이 표가 03~04단계에서 그대로 노드 함수와 라우팅 함수의 설계서가 된다.

02

State 스키마 설계

Shared State & Reducers
목표모든 노드가 공유할 상태 구조를 확정
산출물TypedDict 기반 State 클래스

State는 TypedDict 또는 Pydantic 모델로 정의되는, 모든 노드가 읽고 갱신하는 공유 객체다. 필드마다 리듀서(reducer)를 지정해 여러 노드의 갱신을 어떻게 병합할지 제어한다 — 기본 리듀서는 "마지막 쓰기가 이긴다(last-write-wins)"이며, 메시지 목록처럼 누적이 필요한 필드는 concat 리듀서를 지정한다.[2]

01단계 설계표를 State로 옮기기

from typing import TypedDict, Annotated
from operator import add

class TaskState(TypedDict):
    request: str                 # 입력 — last-write-wins으로 충분
    draft: str                   # draft 노드가 갱신
    approved: bool                # review 노드가 갱신
    revision_count: Annotated[int, add]   # 누적 리듀서 — 반려 횟수 카운트

설계 시 자주 하는 실수

  • 모든 필드를 메시지 목록 하나로 뭉치기 — 디버깅과 서브그래프 격리(08단계)를 어렵게 만든다. 역할별로 필드를 분리하는 것이 낫다.
  • 종료 조건에 필요한 카운터를 State에 두지 않기 — 01단계에서 정한 "최대 3회 반려" 같은 종료 조건은 State 필드(revision_count)로 명시적으로 추적해야 04단계 라우팅 함수에서 판단할 수 있다.
  • 리듀서 없이 병렬 노드에서 같은 필드를 갱신 — 08단계에서 팬아웃(Send) 노드가 동시에 같은 필드를 쓰면 리듀서가 없을 때 값이 유실된다.
03

노드 구현

Node Functions
목표01단계에서 식별한 각 역할을 함수로 구현
산출물graph/nodes.py

노드는 현재 State를 받아 State에 대한 부분 갱신(dict)을 반환하는 순수 함수다. LangChain Runnable이나 컴파일된 서브그래프도 노드가 될 수 있다.[2]

02단계 State에 맞춘 노드 구현

def draft_node(state: TaskState) -> dict:
    draft = llm.invoke(f"다음 요청에 대한 초안을 작성하라: {state['request']}")
    return {"draft": draft.content}

def review_node(state: TaskState) -> dict:
    verdict = llm.invoke(f"다음 초안을 승인/반려로 평가하라:\n{state['draft']}")
    approved = "승인" in verdict.content
    return {"approved": approved, "revision_count": 1}

도구 호출 노드 (ReAct 스타일)

도구를 사용하는 에이전트 노드는 배경 문서에서 다룬 ReAct의 Thought → Action 부분을 구현한다. LangGraph는 ToolNode 프리빌트를 제공해 도구 실행 부분을 직접 구현하지 않아도 되게 한다.

from langgraph.prebuilt import ToolNode

llm_with_tools = llm.bind_tools([search_tool, calculator_tool])

def agent_node(state: AgentState) -> dict:
    response = llm_with_tools.invoke(state["messages"])
    return {"messages": [response]}

tool_node = ToolNode([search_tool, calculator_tool])
설계 원칙 — 노드는 한 가지 역할만 한 노드가 "생성도 하고 검증도 하는" 식으로 역할을 섞으면 01단계에서 그린 그래프와 코드가 어긋나기 시작한다. 노드 하나에 책임 하나를 유지하면, 이후 08단계에서 특정 노드만 별도 서브그래프나 별도 에이전트로 떼어내기 쉬워진다.
04

엣지와 라우팅 구현

Edges & Conditional Routing
목표01단계 전이 조건을 실행 가능한 라우팅 함수로 구현
산출물graph/edges.py, 컴파일된 그래프

엣지는 무조건 엣지(A 다음 항상 B)와 조건부 엣지(라우팅 함수 결과에 따라 다음 노드를 선택)로 나뉘며, 조건부 엣지가 분기를 구현하는 방식이다.[2]

02단계 종료 조건(revision_count)을 반영한 라우팅

from langgraph.graph import StateGraph, END

def route_after_review(state: TaskState) -> str:
    if state["approved"]:
        return "end"
    if state["revision_count"] >= 3:      # 무한 루프 방지 — 01단계 종료 조건
        return "end"
    return "retry"

graph = StateGraph(TaskState)
graph.add_node("draft", draft_node)
graph.add_node("review", review_node)
graph.set_entry_point("draft")
graph.add_edge("draft", "review")
graph.add_conditional_edges(
    "review", route_after_review,
    {"end": END, "retry": "draft"},
)
주의 — 무한 루프 조건부 엣지가 그래프 안에 순환을 만들 때는 반드시 종료 조건(카운터, 타임아웃, 명시적 검증 기준)을 함께 넣는다. 검증 기준 없는 순환은 배경 문서에서 언급한 "무한 루프" 실패 모드를 그래프 레벨에서 재현하는 것과 같다.[20]
05

컴파일과 로컬 테스트

Compile, Invoke, Debug
목표그래프를 컴파일하고 대표 입력으로 검증
산출물tests/test_graph.py, 통과하는 로컬 실행

.compile() 호출 후에야 invoke(), stream(), ainvoke() 등을 지원하는 실행 가능한 그래프가 된다.[2]

app = graph.compile()

# 단발 실행
result = app.invoke({"request": "분기 릴리스 노트 작성", "revision_count": 0})
assert result["approved"] or result["revision_count"] >= 3

# 스트리밍 — 노드별 중간 상태를 확인
for chunk in app.stream({"request": "...", "revision_count": 0}):
    print(chunk)   # {"draft": {...}} 형태로 노드 단위 출력

로컬 디버깅 팁

  • 노드 단위 단위테스트 — 그래프 전체를 돌리기 전에 draft_node(fake_state)처럼 노드 함수를 직접 호출해 검증한다.
  • stream()으로 중간 상태 확인 — 조건부 엣지가 의도한 노드로 분기하는지 각 청크에서 확인한다.
  • LangGraph Studio — 그래프 구조를 시각적으로 보고 단계별로 실행을 따라가며 디버깅할 수 있는 도구로, LangSmith 생태계에 포함되어 있다(09단계에서 함께 다룸).[18]
이 단계에서 멈춰도 되는 경우 01~05단계만으로 완성된 단일 루프 그래프가 요구사항을 충족한다면 06~08단계(영속성/내결함성/멀티에이전트)를 반드시 적용할 필요는 없다. 다음 단계들은 실제로 그 문제가 발생했을 때 추가하는 것이 권장된다.[20]
06

영속성과 Human-in-the-Loop

Checkpointer, Threads, Interrupt
적용 시점세션이 길거나, 재시작 복구가 필요하거나, 사람의 승인이 필요할 때
산출물체크포인터가 연결된 그래프, interrupt 지점

체크포인터는 모든 스텝에서 상태를 저장해, 동일한 thread_id로 다시 호출하면 중단된 지점부터 정확히 재개할 수 있게 한다. LangGraph는 interrupt-and-resume을 1급 시민(first-class primitive)으로 취급한다.[8]

from langgraph.checkpoint.memory import InMemorySaver
# 프로덕션에서는 Postgres/Redis 등 영속 백엔드 사용 (10단계 참고)

checkpointer = InMemorySaver()
app = graph.compile(checkpointer=checkpointer, interrupt_before=["review"])

config = {"configurable": {"thread_id": "case-2026-0823"}}
app.invoke({"request": "...", "revision_count": 0}, config=config)
# review 노드 직전에서 실행이 정지된다.

# 사람이 draft를 확인/수정한 뒤 동일 thread_id로 재개:
app.invoke(None, config=config)
배경 지식과의 연결 LangChain의 2026년 에이전트 엔지니어링 현황 보고서는 프로덕션 인시던트의 60% 이상이 상태 관리 문제와 관련되어 있다고 밝혔다. 06단계를 건너뛰고 바로 08단계(멀티에이전트)로 가면 이 문제가 더 커진다 — 상태 설계(02단계)와 영속성은 노드 수를 늘리기 전에 먼저 안정화해야 한다.[7]
07

내결함성 — 재시도와 오류 처리

RetryPolicy, Timeouts, Error Handlers
적용 시점외부 API/도구 호출이 포함되어 일시적 오류가 예상될 때
산출물노드별 RetryPolicy, fallback 엣지

RetryPolicy는 노드 또는 태스크에 대한 자동 재시도 동작을 제어하는 설정 객체다. 재시도는 그래프 자체의 설정으로 존재하며, 노드 함수 내부에 흩어진 커스텀 로직으로 구현할 필요가 없다.[5][6]

from langgraph.types import RetryPolicy, default_retry_on

def custom_retry_on(exc: BaseException) -> bool:
    if isinstance(exc, MyDomainError):   # 재시도해도 의미 없는 오류는 제외
        return False
    return default_retry_on(exc)

graph.add_node(
    "call_api", call_api_node,
    retry_policy=RetryPolicy(max_attempts=3, retry_on=custom_retry_on),
)

기본적으로 retry_on은 ConnectionError, 5xx HTTP 응답 등 일시적 오류만 재시도하며, ValueError·TypeError처럼 대개 프로그래밍 버그인 예외는 재시도하지 않는다.[4]

재시도 소진 후 처리 — error_handler

from langgraph.errors import NodeError

def on_call_llm_failed(state: AgentState, error: NodeError) -> dict:
    log.error("call_llm 재시도 소진: %s", error.error)
    return {"status": "llm_unavailable"}   # fallback 상태로 전환

graph.add_node(
    "call_llm", call_llm_node,
    retry_policy=RetryPolicy(max_attempts=4),
    error_handler=on_call_llm_failed,
)

error_handler는 재시도가 모두 소진된 후에만 실행되며, 실패 컨텍스트(error.node, error.error)가 주입된다.[4] 처리되지 않은 오류는 그대로 전파되어 그래프 실행을 중단시키므로, 복구가 필요한 노드에는 조건부 엣지로 연결된 fallback 노드를 함께 설계한다.[6]

메커니즘발동 시점용도
retry_policy노드 실행이 예외를 던질 때마다일시적 오류(네트워크, 5xx)를 자동 재시도
timeout노드 실행이 지정 시간을 초과할 때멈춘 HTTP 호출/서브프로세스를 강제 종료
error_handler재시도가 모두 소진된 후복구 상태로 전환하거나 사용자에게 안전한 메시지 반환
조건부 엣지 + fallback 노드State 값에 따라실패를 그래프 레벨에서 다른 경로로 명시적으로 우회

출처.[3][4]

08

멀티에이전트로 확장

Subgraphs, Supervisor / Swarm / Router
적용 시점01단계 체크리스트(역할 분리, 병렬성, 컨텍스트 격리)가 실제로 필요해졌을 때
산출물서브그래프 또는 멀티에이전트 토폴로지
먼저 확인 이 단계로 넘어가기 전에 앞선 개념 문서의 "그래프 승격 신호" 4가지 질문(서로 다른 역할 필요 여부, 병렬 실행 필요 여부, 컨텍스트 격리 필요 여부, 핸드오프 계약을 정의할 수 있는지)에 실제로 "예"라고 답할 수 있는지 확인한다.

8.1 서브그래프로 컨텍스트 격리

슈퍼바이저 패턴에서 전체 메시지 이력이 누적되면 8~12회 왕복 이후 라우팅 정확도가 저하되는 경향이 보고된다. 컴파일된 그래프 전체를 부모 그래프의 노드로 중첩하면 팀 단위로 상태를 격리할 수 있다.[13]

research_team = research_graph.compile()   # 독립적으로 컴파일된 서브그래프

parent = StateGraph(ParentState)
parent.add_node("research_team", research_team)
parent.add_node("writer", writer_node)
parent.add_edge("research_team", "writer")

8.2 슈퍼바이저 패턴

from langgraph.prebuilt import create_react_agent

billing_agent = create_react_agent(llm, tools=billing_tools)
tech_agent = create_react_agent(llm, tools=tech_tools)

def supervisor_node(state: SupState) -> dict:
    decision = supervisor_llm.invoke(state["messages"])
    return {"next": decision.next_worker}

def route(state: SupState) -> str:
    return state["next"]

graph = StateGraph(SupState)
graph.add_node("supervisor", supervisor_node)
graph.add_node("billing", billing_agent)
graph.add_node("tech", tech_agent)
graph.set_entry_point("supervisor")
graph.add_conditional_edges("supervisor", route,
    {"billing": "billing", "tech": "tech", "done": END})
graph.add_edge("billing", "supervisor")
graph.add_edge("tech", "supervisor")

8.3 스웜 패턴 — Command 핸드오프

from langgraph.types import Command
from langchain_core.tools import tool

@tool
def handoff_to_tech(reason: str) -> Command:
    """기술 지원이 필요할 때 기술 에이전트로 전환한다."""
    return Command(goto="tech_agent", graph=Command.PARENT,
                    update={"handoff_reason": reason})

관찰가능성과 평가

Tracing, Metrics, Evals
목표노드/엣지 단위 트레이스 확보, 회귀 방지 평가 체계 구축
산출물LangSmith 프로젝트, 온라인/오프라인 평가 데이터셋

LangGraph와 같은 팀이 만든 LangSmith는 환경변수 설정만으로 모든 LangGraph 노드 실행을 자동으로 추적한다.[17]

export LANGSMITH_TRACING=true
export LANGSMITH_API_KEY=ls_...
export LANGSMITH_PROJECT=my-production-agent
# 이후 별도 코드 수정 없이 모든 LangGraph 노드 실행이 트레이스로 전송된다.

LangSmith는 개별 트레이스부터 프로덕션 전체의 성능 지표까지 시각화하며, 필터링·공유·비교, 대시보드/알림 구성을 지원한다.[15] 주요 활용 방식은 다음과 같다.

  • 디버깅 — 그래프 전체 실행을 트레이스로 재생해 어느 노드에서 잘못된 호출이 발생했는지 특정한다.[16]
  • 오프라인 평가 — 실제 프로덕션 트레이스에 기반한 데이터셋으로 LLM-as-judge, 코드 기반, 멀티턴 평가자를 실행한다.[16]
  • 온라인 모니터링 — 토큰 사용량, P50/P99 지연시간, 오류율, 비용을 대시보드로 추적하고 임계값 초과 시 알림을 구성한다.[19]
  • LangGraph Studio — 그래프 구조를 시각적으로 보며 단계별 실행을 따라가는 디버깅 도구.[18]
배경 문서와의 연결 — 4계층 루프 앞선 개념 문서(§4.2)의 운영/품질/거버넌스/감사 루프는 이 단계의 구체적 구현물이다 — 운영 루프는 지연시간·비용 대시보드, 품질 루프는 오프라인 평가 데이터셋, 감사 루프는 주기적으로 평가 기준 자체를 재검토하는 프로세스에 대응한다.

10.1 프로덕션 체크포인터

06단계의 InMemorySaver는 개발용이다. 프로덕션에서는 Postgres 등 영속 백엔드로 교체해 프로세스 재시작 후에도 스레드 상태가 유지되도록 한다.

from langgraph.checkpoint.postgres import PostgresSaver

with PostgresSaver.from_conn_string(DB_URI) as checkpointer:
    checkpointer.setup()
    app = graph.compile(checkpointer=checkpointer)

10.3 운영 중 피드백 → 01단계로 회귀

09단계에서 수집한 트레이스와 평가 결과는 그래프 설계 자체를 재검토하는 입력이 된다. 특정 노드의 실패율이 높다면 07단계(내결함성)를, 라우팅 정확도가 낮다면 08단계의 토폴로지 선택을, 컨텍스트가 과도하게 누적된다면 02단계(State 스키마)를 재검토한다.

배포 전 최종 점검 리스트

  • 모든 순환 엣지에 명시적 종료 조건(카운터/타임아웃)이 있는가 — 01·04단계
  • 외부 호출이 있는 모든 노드에 RetryPolicy 또는 fallback 경로가 있는가 — 07단계
  • 장시간 세션 또는 재시작 복구가 필요한 흐름에 영속 체크포인터가 연결되어 있는가 — 06·10단계
  • 사람의 승인이 필요한 지점에 interrupt_before가 설정되어 있는가 — 06단계
  • 프로덕션 트레이싱과 최소 하나의 오프라인 평가 데이터셋이 구성되어 있는가 — 09단계
  • 멀티에이전트 구조라면 서브그래프로 컨텍스트가 격리되어 있는가 — 08단계
