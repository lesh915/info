1. 결론 요약

LLM-Wiki는 2026년 4월 공개된 “LLM이 원문을 읽어 지속적으로 갱신되는 상호연결 Markdown 지식베이스를 컴파일한다”는 패턴이다. 원저자가 명시했듯 특정 제품이나 표준이 아니라 구현 아이디어이며, 핵심은 immutable raw sources → LLM-owned wiki → schema/instructions의 3계층과 ingest / query / lint의 운영 루프다. R1

2. LLM-Wiki의 정확한 정의와 경계

Raw Sources
immutable evidence
→
LLM Compiler
extract · reconcile · link
→
Wiki
human-readable compiled knowledge
→
Agent Query
search · read · traverse

전통적 RAG가 질의 시점에 원문 chunk를 찾아 그때마다 합성하는 경향이 있는 반면, LLM-Wiki는 ingest 시점에 지식을 지속적인 중간 표현으로 “컴파일”한다. 페이지 간 연결, entity/concept 요약, 모순과 synthesis가 채팅 세션을 넘어서 유지된다는 것이 핵심이다. R1

2.1 세 계층

계층역할권장 불변식
Source원문, PDF/HTML/회의록/데이터 등원문 불변, 해시 보존, origin/수집시각/권한 기록
WikiLLM이 생성·갱신하는 지식 표현모든 중요한 claim이 source span으로 역추적 가능
Schema / Agent Contract폴더 구조, 페이지 종류, 작성·갱신·질의·검증 규칙작고 명확한 규칙 + 기계적 lint

2.2 중요한 오해

  • “Wiki = Markdown 폴더”가 아니다. 핵심은 지속적 compilation, 연결, provenance, maintenance loop다.
  • “Wiki = Knowledge Graph”가 아니다. Wikilink는 graph-like affordance이지만 완전한 typed KG를 요구하지 않는다.
  • “Wiki = memory”도 아니다. 안정적 domain knowledge와 session/experience memory는 lifecycle과 신뢰도가 다르므로 분리하는 편이 안전하다.

3. 2026 기술 흐름: LLM-Wiki를 둘러싼 변화

2024–2025
Flat RAG → hierarchical / graph / agentic retrieval
GraphRAG, RAPTOR, LightRAG, HippoRAG 등은 chunk-only retrieval의 한계를 보완하기 위해 구조와 반복 검색을 도입했다. Agentic RAG 연구는 retrieval을 계획·반성·도구사용 루프 안으로 이동시켰다. R6 R9
2025

ICML 2025 LaRA는 “긴 context면 RAG가 필요 없다”는 단순 결론을 지지하지 않으며, 모델·context 길이·과제·retrieval 특성에 따라 최적 선택이 달라진다고 보고했다. R7

4. LLM-Wiki 중심 최신 변형 패턴 9종

아래 “성숙도”는 표준화 수준이 아니라 2026-08 현재 구현 근거·연구 근거·운영 현실성을 합친 실무 평가다.

패턴핵심 변화적합한 문제성숙도비판적 관점
1. Baseline Compiled Wiki raw → interlinked Markdown → lint 개인/팀 연구, 중간 규모의 안정적 지식 높음 단순하고 소유권이 명확하지만 대규모 검색과 ACL이 별도 과제다.
2. Hybrid Wiki + RAG Wiki는 curated core, RAG는 long-tail 원문 기업 문서, 수만~수백만 source 권고 복잡도가 증가하지만 Wiki와 RAG의 서로 다른 강점을 가장 현실적으로 결합한다.
3. Retrieval-as-Reasoning Wiki top-k 1회 검색 대신 search→read→follow→sufficiency multi-hop, 비교, 원인-결과, 탐색형 질문 유망 2026 preprint에서 성능 향상이 보고됐으나 독립 재현과 비용 검증이 더 필요하다. R2
4. Self-Correcting Wiki Error Book / lint / recurring repair 장기 운영, 자동 ingest 유망 “자기 수정”은 잘못된 규칙도 누적할 수 있으므로 deterministic validator와 semantic judge를 분리해야 한다.
5. Graph-backed Wiki Markdown 페이지 + typed entity/relation graph 복잡한 관계, lineage, dependency, multi-hop 선택적 graph를 모든 도메인에 강제하면 ontology debt와 추출 오류가 커진다. GraphRAG 공식 저장소도 연구/유지보수 모드임을 명시한다. R9
6. Temporal / Bitemporal Wiki valid time + transaction time, 사실 overwrite 금지 정책, 운영상태, 계약, 고객/시스템 상태 변화 강력한 추세 시간 질의를 정확히 할 수 있으나 데이터 모델이 복잡해진다. Temporal graph memory 연구가 활발하다. R10
7. Provenance-first Wiki page citation보다 claim→source span을 1급 객체로 취급 감사, 규제, 연구, 중요 의사결정 강력 권고 저장량과 추출 비용이 늘지만 “어디서 나온 주장인가”를 시스템적으로 검증할 수 있다. W3C PROV의 entity/activity/agent 모델도 참고 가능하다. R11
8. Multimodal Wiki 텍스트뿐 아니라 표·그림·도식·layout을 독립 evidence로 유지 PDF, 매뉴얼, 기술문서, 차트 중심 문서 성장 중 OCR→텍스트 변환만으로는 정보 손실이 크다. ACL 2026 survey는 graph/agentic framework까지 포함해 멀티모달 RAG가 발전 중이라고 정리한다. R8
9. MCP-served Wiki Wiki를 search/read/source/lint 도구로 표준 노출 여러 agent/IDE/업무시스템 공유 권고 프로토콜은 성숙 중이며 breaking change 관리가 필요하다. 최신 spec/roadmap을 따라 version negotiation과 최소 tool surface를 유지해야 한다. R4 R15

5. 비판적 평가: 무엇이 실제 이점이고 무엇이 과장인가

5.1 “컴파일하면 query가 싸진다”는 가설은 현재 반증되었다

24개 논문·13개 질문의 소규모 사전등록 비교 연구에서 Wiki는 구축비가 크게 높았고, 예상과 달리 질의 시 토큰 사용량도 Vector RAG보다 약 21배 높았다. 또한 decomposition-RAG는 Wiki의 cross-paper synthesis 장점 대부분을 더 낮은 비용으로 회복했다. 다만 claim-level citation support에서는 Wiki에 장점이 남았다. R3

해석: “구조화된 Wiki 자체가 성능 원인”이라고 단정하면 안 된다. 일부 이점은 query decomposition, iterative reading, better prompting 등 agent workflow에서 기인할 수 있다.

5.2 그래프는 만능 인덱스가 아니다

Microsoft GraphRAG는 raw text에서 graph를 추출하고 community hierarchy/summaries를 활용하는 대표적 구조화 RAG이지만, 공식 저장소는 현재 “largely in maintenance mode”이며 indexing 비용에 주의하라고 명시한다. 이는 그래프 접근이 무효라는 의미가 아니라, 그래프 구축 비용과 복잡도 대비 실제 질의 가치를 측정해야 한다는 신호다. R9

5.3 긴 컨텍스트도 RAG의 단순 대체재가 아니다

ICML 2025 LaRA는 11개 LLM을 평가해 RAG와 long-context 중 하나가 항상 우월하지 않으며 과제, 모델, context 길이와 retrieval 품질의 상호작용이 중요하다고 결론지었다. 따라서 LLM-Wiki query에서도 “페이지 전체를 모두 context에 넣기”보다 query-specific routing이 필요하다. R7

5.4 LLM-maintained knowledge는 “동의하는 오류”가 가장 위험하다

여러 wiki page가 동일한 잘못된 synthesis를 반복하면 내부 consistency는 높아 보이지만 실제 source와는 어긋날 수 있다. 따라서 cross-page consistency만으로 품질을 평가하지 말고, claim-level source entailment와 source freshness를 별도 측정해야 한다.

9.2 “업데이트”와 “재작성”을 구분

좋은 업데이트

  • claim 단위 delta 계산
  • 근거 source 추가/제거가 명확
  • 기존 문장 중 영향 범위만 수정
  • diff와 generated-by metadata 기록

위험한 업데이트

  • 새 source 1개마다 전체 page를 자유 재생성

  • 과거 사실을 현재 사실로 덮어씀
  • 모델이 “충돌 해결”을 이유 없이 단정

10. Query / Traversal 파이프라인

2026 LLM-Wiki 연구에서 중요한 변화는 retrieval을 하나의 top-k 호출이 아니라 search → read → link-follow → evidence sufficiency → re-plan 과정으로 보는 것이다. 해당 preprint는 이를 “Retrieval-as-Reasoning”으로 명명하고 Wiki에 search/read 도구를 노출했다. R2

10.1 Router

질의 유형우선 경로예
정확한 entity/용어alias/title FTS → direct page read“Lot Hold 정의?”
키워드/문장 찾기BM25/FTS → source span“rebuild nightly 언급 위치?”
의미적 유사 검색dense retrieval + rerank표현이 다른 동일 개념
관계/multi-hopwiki traversal + graph expansionA 시스템 장애가 B 정책에 미친 영향
전체 경향/비교directory index → scoped aggregation → source checks“지난 분기 공통 장애 패턴”

단일 큰 문서 심층 이해long-context or hierarchical sections한 계약서 전체 분석

11. AGENTS.md / Schema 설계 가이드

OpenAI의 2026 agent-first engineering 사례는 거대한 instruction file이 context를 잠식하고 stale해지며 검증하기 어렵다고 보고, AGENTS.md를 약 100줄의 “map”으로 사용하고 깊은 문서는 구조화된 docs에 둔다. R5

11.1 AGENTS.md에는 “불변식 + 탐색법 + 도구 계약”만 둔다

# Knowledge Agent Contract

## Mission
Use the repository as the system of record.
Never invent facts that are not supported by evidence.

## Read order
1. Read wiki/_index.md.
2. Resolve aliases via dictionaries/aliases.yaml.
3. Read only pages relevant to the task.
4. For load-bearing claims, call wiki_get_evidence.

## Invariants
- sources/immutable is read-only.
- Every important factual claim must reference at least one claim_id.
- Never overwrite historical facts; supersede them.
- Do not merge ambiguous entities automatically.
- ACL filtering occurs before ranking and before generation.
- A generated summary is not evidence.

## Write workflow
propose_patch -> validate_schema -> validate_citations
-> validate_links -> conflict_check -> commit

## Escalate
Escalate when a source is untrusted, claims conflict without a time/version explanation,
or a write changes policy, identity, access, or irreversible business meaning.

12. 검색·RAG 선택 가이드

12.1 “Embeddings first”가 아니라 “signal fusion”

정확한 이름·코드·약어가 많은 지식베이스는 lexical signal이 매우 강하다. 따라서 title/alias/tag/identifier를 높은 가중치로 두고, semantic vector는 표현 변형을 보완하는 수단으로 사용한다. 최신 agent memory 구현도 semantic/BM25/entity signal 결합을 채택하는 흐름을 보인다. R14

12.2 규모별 기본 선택

규모/성격기본 구성추가 조건
수십~수백 페이지index.md + grep/FTS + direct readvector DB부터 도입하지 않는다.
수천~수만 페이지FTS/BM25 + dense + rerankpage/section level을 함께 인덱싱

대규모/빠른 변화Wiki core + raw RAG long tailfresh raw source를 Wiki보다 우선할 조건 정의
긴 단일 문서long-context + section mapLaRA가 보여주듯 LC/RAG는 task별 routing 필요. R7

13. 시간·모순·폐기(Supersession) 관리

장기 지식 시스템에서 “현재 맞는 사실”과 “당시에 맞았던 사실”은 다르다. 2025~2026 agent memory 연구는 temporal knowledge graph, graph-based memory, memory evolution을 핵심 과제로 다룬다. R10 R13

13.1 Bitemporal 최소 모델

시간의미예
valid_time현실에서 사실이 유효했던 시간정책 v3는 6/1~7/31 유효
transaction_time시스템이 그 사실을 알고 저장한 시간v3 문서를 6/10에 ingest

이렇게 하면 “6월 15일 실제 정책은?”과 “6월 5일 당시 시스템이 알고 있던 정책은?”을 구분할 수 있다.

13.2 모순 상태 머신

new claim
→
compare scope/time/entity
→
supports / contradicts / supersedes / independent
→
publish both + resolution metadata
모순을 발견했다고 과거 claim을 삭제하지 않는다. superseded, retracted, disputed 상태와 이유/근거/시간을 남기고 기본 query에서 현재 active fact를 우선하도록 한다.

17. 보안·권한·데이터 Poisoning

LLM-Wiki는 agent가 지식을 “기록”하기 때문에 일반 RAG보다 잘못된 정보가 장기적으로 증폭될 위험이 있다. OWASP는 RAG/embedding 시스템에서 unauthorized access, cross-context leakage, poisoning, embedding inversion을 주요 위험으로 지적하고 permission-aware storage, source validation, classification, immutable logs 등을 권고한다. R17

17.1 필수 통제

  • ✓ ACL-before-retrieval: 권한 필터를 ranking 후가 아니라 후보 생성 전에 적용.
  • ✓ Source trust tier: verified / internal / external / untrusted / quarantined.
  • ✓ Indirect prompt injection 격리: source text를 agent instruction으로 해석하지 않음.
  • ✓ Write isolation: query agent와 curator/ingest agent의 권한 분리.
  • ✓ Immutable audit: 어떤 모델/프롬프트/도구가 어떤 claim을 생성·변경했는지 기록.
  • ✓ Tenant isolation: vector/graph/FTS 모든 파생 index에서 동일 ACL을 보존.
  • ✓ Deletion workflow: source 삭제 요구가 발생하면 Wiki/claim/index 파급범위를 추적 가능하게 설계.

19. 실패 패턴과 왜 실패하는가

1) AGENTS.md 비대화

모든 도메인 지식을 한 파일에 넣으면 context를 잠식하고 stale rule을 구별하기 어렵다. R5

2) Wiki가 evidence를 대체

요약이 요약을 인용하면 오류가 자기증폭된다. Wiki는 source를 가리키는 compiled layer여야 한다.

3) 새 source마다 전체 페이지 재생성

불필요한 문장 drift, citation drift, diff noise가 커진다. claim delta 기반 patch가 낫다.

4) 모든 관계를 graph로 강제

ontology와 entity resolution 비용이 질의 가치보다 커질 수 있다. graph는 필요한 관계 질의에만 적용한다.

5) Vector index를 source of truth로 사용

embedding/model 변경 시 의미가 바뀌고 audit가 어렵다. index는 재생성 가능한 파생물이어야 한다.

6) 최신 source가 자동으로 진실

최신은 더 새로울 뿐 더 정확하다는 뜻이 아니다. authority와 valid time을 별도로 평가한다.

7) Agent가 충돌을 몰래 해결

상충 claim을 삭제하지 말고 disagreement/supersession을 표시한다.

8) LLM-as-judge만 사용

비교 연구에서도 평가 기준과 judge에 따라 순위가 달라졌다. claim-level deterministic checks와 human sample calibration이 필요하다. R3

20. Production Ready 체크리스트

Source & Provenance

  • □ 모든 source에 immutable ID/hash가 있는가?
  • □ origin, 수집 시각, published/valid time, ACL이 기록되는가?
  • □ 중요한 claim이 정확한 source span으로 역추적되는가?
  • □ source 삭제/정정 시 파생 claim/page/index 영향범위를 찾을 수 있는가?

Knowledge Structure

  • □ alias/entity resolution 규칙이 domain별로 정의됐는가?
  • □ page type과 required frontmatter가 schema로 검증되는가?
  • □ historical fact를 overwrite하지 않는가?
  • □ orphan/dangling/stale/contradiction lint가 자동화됐는가?

Retrieval & Agent

  • □ query router가 lexical/dense/graph/long-context를 task별로 선택하는가?
  • □ agent가 evidence sufficiency를 확인하고 무한 탐색을 멈추는가?
  • □ tool call budget, latency, token cost를 기록하는가?
  • □ 답변의 citation이 page가 아니라 source evidence까지 내려가는가?

Security & Governance

  • □ ACL이 retrieval 전에 적용되는가?
  • □ untrusted source의 prompt-like content가 instruction으로 승격되지 않는가?
  • □ read agent와 write/curation agent 권한이 분리됐는가?
  • □ 정책/민감/비가역적 변경은 별도 승인 또는 강한 validation을 거치는가?

Evaluation

  • □ fact lookup, multi-hop, temporal, global synthesis, negative/unanswerable test set이 있는가?
  • □ retrieval recall과 answer correctness를 분리 측정하는가?
  • □ claim citation support rate를 별도 측정하는가?
  • □ 모델/embedding 변경 시 regression eval이 자동 실행되는가?
